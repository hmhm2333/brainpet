# BrainPet V1 产品需求与开发计划

状态：V1 开发验收完成；Runtime/Stage 基础设施门与两项任务样本已通过，外部物理放行待复核
日期：2026-08-14
适用分支：`codex/foundation`

## 1. 结论

BrainPet V1 应交付一个完成度足够高的垂直切片，而不是一个 UI 简陋的技术演示，也不是一个尚未验证的认知游戏库。

V1 的第一优先级不是制作两款游戏，而是先完成一个稳定、可复用的游戏 Runtime 和小型桌面舞台。Go/No-Go 与持续更新是这个基础设施上的首批内容模块，也是验证基础设施是否真正通用的两个验收样本。在 Runtime 基础设施验收门通过前，不进入正式游戏内容开发。

截至 2026-08-14，代码已按该顺序完成：Host Adapter、Runtime Core、Task Contract、Stage Exerciser 与基础设施门先落地，之后才接入 `cargo-signal` 和 `pack-refresh`。验收证据与可重复命令见 `docs/brainpet-runtime.md`。

首版只做两款短任务：

1. 一款简单、低学习成本的 Go/No-Go 游戏；
2. 一款以持续更新为核心的工作记忆游戏，不采用 DCCS 或 n-back/延迟反应。

两款游戏共享同一个桌宠入口、角色、像素视觉、训练舞台、结果反馈和本地记录系统，不建设宏大世界观。用户点击宠物身上显眼的训练部位后，系统随机打开其中一款游戏的当前关卡。每轮默认 45–60 秒，结束后显示通关、分数、个人纪录和一次简短打卡，随后由宠物反馈并收起舞台。

V1 的核心产品命题不是“有两个任务”，而是证明以下转换链路成立：

```text
认知任务范式
  -> 保留不可污染的任务骨架
  -> 选择与骨架同构的游戏隐喻
  -> 将刺激和反应映射为世界中的对象与动作
  -> 用场景后果替代抽象对错提示
  -> 将难度参数转成可感知但可追溯的游戏变化
  -> 由宠物承接开始、反馈与结束
```

## 2. 已确认、暂定与延期

### 已确认

- 基于 OpenPets 源码 fork，并以第一方训练插件承载任务，不另装一个独立桌面应用。
- 训练入口是宠物身体或配件上的显眼部位，不是系统托盘菜单或网页按钮。
- 训练舞台是宠物附近的小型透明、无边框窗口，不全屏，不出现独立浏览器页。
- 舞台面积约占当前屏幕工作区的九分之一，即宽高约各占三分之一，并设置合理尺寸上下限。
- 视觉要达到可发布的 2D 像素游戏完成度，整体气质偏传统任天堂式的轻巧、明确和有角色感。
- 首发任务为 Go/No-Go 与工作记忆各一款。
- 点击后默认随机进入一款游戏，不设置游戏大厅、地图或选关页。
- 第一关本身承担规则测试和学习，不另设教程页或规则演示流程。
- 分数与宠物要有即时互动，但 V1 只保存本地数据。
- V1 不做认知训练内容体系、长期课程和完整自适应推荐。

### 暂定

- 默认单轮 45–60 秒；未来是否增加更长模式取决于真实使用数据。
- 鼠标为必备输入，键盘为推荐输入；触屏不作为 Windows V1 的验收阻塞项。
- 第一版通过同一宠物角色、像素比例、调色板、道具和反馈动作形成一致性，不建立剧情世界观。
- 难度采用透明、确定性的分段升降，而不是黑箱推荐。

### 延期

- 账号、云同步、跨设备、联网天梯、好友 PK、反作弊。
- 商店、订阅、付费游戏、宠物经济系统。
- 每日训练计划、能力雷达、复杂成长树、长期课程推荐。
- 医疗、诊断、治疗、智商提升或可迁移效果承诺。
- 第三方任务市场和开放 SDK。
- 地图、剧情、NPC、背包养成、装备、任务列表和完整冒险系统。
- 单独的教程、规则说明页或必须看完的演示动画。

## 3. 调研问题：怎样把范式变成游戏

本次竞品参考不以首页 UI、训练计划或商业结构为主，而以“抽象认知任务怎样被改造成具体游戏”为主。

### 3.1 魔鬼脑训练：先保留操作骨架，再换成直观对象

任天堂的工作记忆任务并不都依赖重度世界观。它经常保留极简、清晰的任务骨架，再用一个一眼可懂的现实动作来解释它：

- n-back 式延迟回答变成“记住当前题，回答之前的题”；
- 位置更新变成猫、老鼠与遮挡板；
- 对象追踪变成球与杯子的移动；
- 空间序列变成方块消失、移动后按顺序找回；
- 语词保持变成朗读过程中记住带标记词语。

这类设计的价值不在画面复杂，而在于隐喻与任务规则高度同构：玩家理解“我在追踪什么、何时作答、为什么错”几乎不需要额外说明。官方页面列出的八种任务也说明，同一工作记忆目标可以通过对象、通道和反应形式形成多个不同游戏，而不是只替换皮肤。[任天堂魔鬼训练任务列表](https://www.nintendo.com/tw/brain_training/training/training_onitore.html)

可借鉴的方法：

1. 一项核心认知操作对应一个主动作；
2. 题材帮助理解规则，不制造额外规则；
3. 难度变化直接对应需要保持、更新或抑制的信息量；
4. 角色负责挑战、鼓励与仪式感，不挤进刺激区干扰作答。

### 3.2 Lumosity：寻找与实验范式结构相同的生活场景

Lumosity 最典型的做法不是给实验材料换图，而是寻找一个结构同构的生活或自然场景：

| 原任务骨架 | 游戏化表达 | 没有改变的核心 |
| --- | --- | --- |
| Flanker：判断中心刺激，忽略两侧冲突刺激 | `Lost in Migration`：判断领头鸟方向，忽略鸟群干扰 | 中心目标、相容/不相容试次、方向反应、反应时 |
| 持续更新：记住已出现对象，避免重复选择 | `Tidal Treasures`：潮池不断冲来宝物，只拾取未选过的宝物 | 对象保持、更新、相似项辨别、重复错误 |
| 空间位置短时保持 | `Memory Matrix`：记住网格中亮起的位置 | 呈现、保持、位置重建、负荷数量 |
| 2-back | `Memory Match`：判断当前符号是否与前两个相同 | 序列更新、匹配判断、n 值、时间窗 |

`Lost in Migration` 官方说明明确写出了从 Eriksen Flanker 字母任务到鸟群方向任务的替换关系；它的成功点是“鸟群”天然解释了中心目标和周边干扰，而不是额外增加故事操作。[Lumosity 对该转换的说明](https://www.lumosity.com/en/blog/new-insight-lost-in-migration/) `Tidal Treasures` 则把不断更新“见过的对象集合”变成潮池拾宝，物体逐渐增多、越来越相似，分别承载记忆负荷与视觉辨别难度。[Tidal Treasures](https://www.lumosity.com/en/brain-games/tidal-treasures/)

可借鉴的方法：

1. 先写出范式的不变量，再找结构相同的世界事件；
2. 让正确反应推动世界继续运行，让错误在世界中产生可理解后果；
3. 场景对象可以丰富，但任务无关的辨别负担必须受控；
4. 同一题材中可以通过数量、相似度、速度和干扰关系承载不同难度维度。

### 3.3 未来之光：适合作为任务库包装参考，不作为主要转换证据

公开资料能确认未来之光使用大量短游戏、六类能力、每日计划与进度可视化，但不足以严谨还原每款游戏从实验范式到游戏机制的设计过程。[未来之光 App Store 页面](https://apps.apple.com/cn/app/%E6%9C%AA%E6%9D%A5%E4%B9%8B%E5%85%89-%E6%9B%B4%E8%81%AA%E6%98%8E%E7%9A%84%E8%84%91%E5%8A%9B%E6%B8%B8%E6%88%8F/id1416993897)

因此 V1 只借鉴它的两点：每个任务有独立、可识别的视觉主题；用户能迅速看到一次训练完成了什么。其重型 App 壳、能力首页、社交与 PK 不进入 V1。

### 3.4 无疆与好未来原始材料：把游戏包装与任务变量分层

本次复核的高价值原始材料包括：

- `基于认知负荷的难度设计20220113.pptx`
- `认知产品中台模式的经验和思考20220113.pptx`
- `ADHD训练的新特性.pptx`
- `星际探索引导流程V1.2.docx`
- 好未来早期 App、Toolbox 与研发流程材料

这些材料对 BrainPet 最重要的不是旧视觉，而是生产方法：

- 难度不是一个数字，而是一组参数向量；数量、速度、持续时间、信噪比、路径交叉、呈现规则和附加任务会改变不同类型的负荷。
- 游戏化可以“逻辑不变、贴图改变”，但呈现、交互、反馈、节点逻辑与埋点必须分别配置和版本化。
- 引导不应只靠说明文字；旧版“星际探索”把复杂规则拆成对象出现、动画提示、受控练习、减少提示、完整试次四步。
- 训练进阶可以是切片和波浪，而不是永远单调增加。
- 图形化、具象化和 2D 表达更适合短任务，但不能让游戏外在负荷遮蔽核心认知负荷。

这与 Lumosity 的“结构同构隐喻”可以合并成 BrainPet 自己的方法：**先冻结任务活性成分，再把刺激、反应与反馈逐一映射到游戏世界；所有装饰元素都必须证明自己没有改变核心任务。**

## 4. BrainPet 的任务游戏化转换规范

每款任务进入视觉设计前，必须先填写一张 `Task-to-Game Mapping`，包含以下内容。

### 4.1 范式不变量

- 目标认知操作；
- 目标刺激与非目标刺激；
- 刺激呈现时序；
- 可用反应与禁止反应；
- 正确、错误、遗漏和抢答的定义；
- 必须记录的反应时起点与终点；
- 可调难度参数；
- 不允许引入的额外认知要求。

### 4.2 游戏映射

- 玩家在世界里扮演什么；
- 目标刺激变成什么对象；
- 玩家反应变成什么动作；
- 不反应在故事中代表什么；
- 正确与错误如何形成即时、可理解的场景后果；
- 难度变化怎样在世界中可见；
- 宠物怎样发起、旁观、反馈和收尾。

### 4.3 污染检查

以下任一问题为“是”，就需要回退设计：

- 玩家是否必须读懂额外文字才能完成本来不需要语言的任务？
- 美术差异是否让某一类刺激更显眼或更难辨认？
- 动画是否改变刺激暴露时间或遮挡下一试次？
- 得分特效是否泄露下一次应答规则？
- 场景中是否出现与目标竞争注意的无关运动？
- 玩家是否能通过故事规律而不是目标认知操作取得高分？
- 低性能设备是否会让帧率变化进入反应时测量？

### 4.4 设计原则

1. **同构，不是换皮。** 隐喻必须解释任务结构。
2. **一个试次，一个主动作。** 短局中不加入移动、收集、养成等第二套操作系统。
3. **反馈属于世界。** 优先表现“接住/漏掉、放行/拦住、装入/溢出”，而不是浮出一个红叉。
4. **宠物在边缘，不在刺激区。** 宠物增强情绪反馈，但不能成为无关干扰。
5. **视觉变化可追溯。** 每个影响辨别、速度或注意的变化都对应参数。
6. **先形成一个好游戏，再复用生产线。** V1 不为了未来插件市场牺牲首款体验。

## 5. V1 用户体验

### 5.1 核心场景

用户让 Codex、Claude 或其他 Agent 执行一个需要等待的任务。桌宠仍在桌面活动，训练配件出现轻微待机信号。用户点击配件，宠物用一个 300–600ms 的短动作展开训练舞台，系统立即随机进入 Go/No-Go 或持续更新的当前关卡。玩家无需选游戏、选关、看教程或离开当前桌面。

### 5.2 单次流程

```text
宠物待机
  -> 点击训练部位
  -> 宠物准备/投掷动画
  -> 舞台展开
  -> 1–2 秒关卡名与一句规则
  -> 45–60 秒当前关卡（第一关即规则测试）
  -> 通关、分数、个人纪录与今日打卡
  -> 宠物即时反应
  -> 自动收起，或选择原关重试
```

### 5.3 状态要求

| 状态 | 用户看到什么 | 系统要求 |
| --- | --- | --- |
| 可训练 | 配件有低频、非打扰提示 | 不抢焦点，不持续闪烁 |
| 展开 | 宠物动作与舞台生成连贯 | 舞台固定在同一显示器可见区域 |
| 关卡开场 | 关卡名与一句短规则 | 1–2 秒后自动开始，不阻塞操作 |
| 第一关 | 极易区分的刺激、慢节奏和即时反馈 | 关卡本身验证用户是否理解，不另开教学模式 |
| 正式局 | 游戏主体、核心对象、极少 HUD | 60 FPS 目标，输入与计时确定 |
| 结算 | 本局结果、最好成绩或难度变化 | 2–4 秒内读完，可立即关闭 |
| Agent 完成 | 不强制中断当前试次 | 默认结束当前短局后提醒；可手动立即退出 |
| 失焦/锁屏 | 暂停并明确恢复 | 不把失焦时间计入反应时 |
| 关闭 | 舞台收回宠物附近 | `Esc`、关闭按钮、宠物离开均可安全结束 |

## 6. 两款首发任务

具体训练阈值由后续任务设计评审确定。V1 先冻结以下两个具体游戏机制和共同视觉载体。

### 6.1 Task A：Go/No-Go

#### 任务骨架

- 连续出现单个刺激；
- Go 刺激需要在时间窗内做一次反应；
- No-Go 刺激需要抑制反应；
- 记录命中、遗漏、虚报、抢答和反应时；
- 主要难度变量包括刺激间隔、反应窗、Go/No-Go 比例、刺激相似度和规则保持时长。

#### 已确认游戏机制：装箱，还是放过（工作名）

宠物的小工作台依次送出单个物品。符合当前规则的目标物出现时，玩家点击舞台任意有效区域或按下空格，将它装入箱中；非目标物出现时保持不动，让它自然离开工作台。

这个隐喻与 Go/No-Go 同构：

- Go = 点击/空格，把目标装箱；
- No-Go = 保持不动，让非目标离开；
- 命中 = 物品进入箱中并形成短促连贯反馈；
- 虚报 = 非目标被误装，箱子轻微卡住；
- 遗漏 = 目标从工作台滑走；
- 难度 = 呈现节奏、反应窗、比例和对象相似度，而不是增加移动或瞄准。

第一关使用形状与颜色均明显不同的目标和非目标，节奏较慢，并保留一个极简规则提示。第一关通过后才逐渐缩小刺激差异、缩短时间窗或改变比例。不得只靠红绿颜色区分。

### 6.2 Task B：工作记忆

#### 已确认骨架：固定容量的持续更新

任务维持一个固定容量的物品序列。新物品进入时最旧物品移出，玩家需要持续更新当前行囊内容，并判断刚被移出的对象。

这不是翻牌配对，也不是固定清单回忆：有效集合每轮滚动变化，每次更新都会改变下一次判断所依据的记忆状态。

核心记录包括正确识别移出对象、错误选择、遗漏、当前容量与有效决策时间。主要难度变量包括集合容量、对象相似度、候选数量和呈现节奏；每个 block 只调整一个主要变量。

#### 已确认游戏机制：行囊不重样（工作名）

宠物的行囊保持三个可见槽位。新物品从右侧进入、最旧物品从左侧移出，玩家从两个候选中判断刚被移出的对象。第一关用差异明显的符号和较长反应窗直接完成规则测试。

游戏世界必须清楚承载以下映射：

- 新对象 = 从右侧进入行囊；
- 最旧对象 = 从左侧移出并成为本轮目标；
- 当前槽位 = 下一轮需要继续保持和更新的集合；
- 错误选择 = 轻量显示正确移出对象，不打断下一轮；
- 难度提升 = 容量、相似度、候选数量或反应窗变化，而不是加入第二套操作。

第一关只使用少量、差异明显的物品和两个候选位，不设置强时间压力。用户通过直接作答理解滚动更新，不观看额外演示。正式参数发布前由认知任务负责人确认容量、更新时序、候选生成和难度参数。

### 6.3 随机进入与关卡打卡

- 每款游戏独立保存当前关卡、每关最高分、通关状态和参数版本；
- 点击训练入口后，系统从两款游戏的当前可玩关卡中随机选择一个；
- 随机不是完全无状态：若另一款可用，应避免连续三次出现同一游戏；
- 通关后只推进被抽中游戏的关卡，不产生跨任务等级；
- 失败后结算页提供一次“再试本关”，否则舞台自动收起；
- 每完成一关只显示一次轻量的“今日已完成 N 关”，不提供地图、日历页或任务清单；
- 同一关的刺激由 seed 随机生成，重复挑战仍可冲击本关个人最高分。

## 7. 视觉与声音方向

### 7.1 “任天堂化”的可执行定义

这里指产品品质和表达原则，不复制任天堂的角色、画面、名称、音效、关卡数据或独特交互。V1 的一致性来自角色与视觉系统，而不是宏大世界设定：

- 同一个宠物角色承担邀请、出题、惊讶和庆祝；
- 操作规则能通过动作演示理解；
- 每次输入都有扎实、短促、可预测的视听反馈；
- 失败轻巧、清楚、可恢复，不羞辱用户；
- 界面层级少，颜色和动画服务于当前动作；
- 两款游戏复用工作台、行囊、箱子和小道具，但保持不同的主操作；
- 局短但有开始、连续反馈和结束，不增加剧情段落。

### 7.2 像素设计系统

- 2D sprite/tile 表达，整数倍缩放，避免像素边缘模糊；
- 先定义逻辑画布，再适配窗口尺寸；建议从 320×180 或相近 16:9 逻辑分辨率开始视觉实验；
- 共享有限主调色板，每款任务只增加少量场景色；
- 动画以 6–12 帧短动作为主，关键反馈可使用轻微停帧、挤压和粒子；
- HUD 只保留剩余时间、连贯反馈和必要的当前规则；
- 中文说明使用高可读字体，不强行把小字号正文做成低清像素字；
- 音效短、干净、可独立静音；不使用持续背景音作为完成任务的必要线索。

### 7.3 明确避免

- 半透明网页卡片、圆角 Dashboard、渐变 SaaS 首页风格；
- 全屏手游大厅、能力雷达和多层菜单；
- 地图、冒险路线、角色对话和选关界面；
- 医疗仪器、脑电图、实验室测试感；
- 纯贴图换皮但规则仍是抽象符号点击；
- 过多漂浮数字、徽章和货币遮挡任务；
- 复刻马里奥、宝可梦、脑训练博士等可识别 IP 表达。

## 8. 宠物与分数的互动

V1 的宠物互动只构成一个短反馈闭环，不建立经济系统。

### 本地反馈层级

- 完成：宠物一定给予正向确认；
- 表现稳定：宠物出现更强的庆祝动作；
- 刷新个人最好：舞台或宠物产生一次稀有短动画；
- 连续完成：宠物配件出现短时视觉变化；
- 中断或低分：宠物不生病、不挨饿、不责备，只提供普通收尾。

### 分数原则

- 原始任务指标与娱乐分数分开存储；
- 娱乐分数可以综合准确率、速度和难度，但公式必须版本化；
- 两款游戏的原始分数不可直接横向比较；
- V1 只显示本任务内的最好成绩、当前难度或个人变化；
- 不设计全球总脑力分，也不暗示 IQ 或真实能力提升。

## 9. 技术需求

### 9.1 分层原则

```text
OpenPets Host Adapter
  热点、桌面窗口、宠物反应、插件沙箱
                |
                v
BrainPet Runtime
  生命周期、时钟、输入、任务注册、session、存储
                |
                v
BrainPet Stage
  渲染、场景、sprite、动画、音频、HUD、资源加载
                |
                v
Task Modules
  试次生成、任务参数、作答规则、任务指标
```

基础设施必须满足三条硬边界：

- Host 不知道 Go/No-Go 或持续更新的任务规则；
- Runtime 和 Stage 不包含任何首发游戏的特殊分支；
- 新任务只能通过注册模块和资源进入，不得要求修改桌面窗口、计时器、输入系统或持久化主流程。

### 9.2 OpenPets Host Adapter

Host 负责桌面级能力，不包含具体任务规则：

- 为宠物定义稳定的训练热点 ID 和命中区域；
- 区分拖动、普通点击和训练点击；
- 允许热点绑定到宠物配件或身体相对坐标；
- 创建透明、无边框、置顶、无任务栏图标的锚定训练窗口；
- 保证窗口不越出当前显示器可用区域；
- 支持透明区域点击穿透、焦点获取、失焦暂停和生命周期清理；
- 向沙箱插件提供最小化消息接口；
- 通过 feature flag 可完全恢复原 OpenPets 行为。

### 9.3 BrainPet Runtime Core

Runtime 是 V1 最重要的可复用资产，负责所有游戏共享的运行逻辑：

- 统一状态机：`idle -> opening -> ready -> running -> paused -> settling -> closing`；
- 单调时钟、帧调度、刺激计划时间和实际呈现时间；
- 鼠标、键盘输入归一化及输入时间戳；
- 失焦、锁屏、显示器变化、宠物移动和 Agent 完成时的暂停/恢复策略；
- task registry、随机选择、防连续重复和模块版本校验；
- session 创建、seed、生命周期、异常终止和恢复；
- 原始事件、任务结果、娱乐分数和宠物事件的分层持久化；
- 难度策略接口，而不是某一任务的阈值实现；
- 崩溃隔离、诊断日志和开发模式状态检查。

### 9.4 BrainPet Stage

Stage 是所有小游戏共享的 `1/9` 屏幕游戏舞台：

- 逻辑分辨率、整数倍像素缩放和 Windows DPI 适配；
- scene、layer、sprite、animation、particle 和 camera 的最小抽象；
- 统一资源 manifest、预加载、缓存、版本和缺失资源回退；
- 统一音效总线、静音、音量、降低动画和可辨识度设置；
- 统一关卡开场、倒计时、暂停、结算、重试和关闭组件；
- 统一输入命中区域和透明区域点击穿透边界；
- 统一帧率、掉帧、卡顿和资源加载耗时监测；
- 任务 renderer 只能操作被授权的舞台 API，不能控制桌面窗口或伪造成绩。

Stage 不需要成为通用游戏引擎。V1 只建设两款短任务确定需要的稳定能力，但这些能力必须以任务无关方式实现。

### 9.5 Task Module Contract

每个任务模块至少提供：

- 稳定 ID、语义版本、资源版本；
- `Task-to-Game Mapping` 文档；
- 参数 schema 与合法范围；
- 根据 seed 确定性生成 session；
- 第一关规则测试与正式试次模式；
- 刺激事件、输入事件与结果事件；
- 原始指标与娱乐分数的分离输出；
- 暂停、恢复、提前结束和失焦处理；
- renderer 不得直接修改持久化成绩。

### 9.6 Stage Exerciser 与开发工具

在制作正式游戏前，先实现一个仅开发模式可见的 `Stage Exerciser`。它不是第三款游戏，也不得进入用户版本；它只用于确定性地验证基础设施：

- 打开、关闭、重复打开和宠物移动后的重新锚定；
- sprite 加载、移动、遮挡、动画、粒子和音效；
- 鼠标/键盘输入及时间戳回显；
- 45–60 秒时钟、暂停、恢复、提前结束和结算；
- 固定 seed 的事件序列与结果校验；
- 丢资源、renderer 异常、掉帧和失焦时的安全降级；
- 不同 DPI、多显示器和屏幕边缘下的缩放与布局。

同时提供最小开发工具：任务参数面板、固定 seed 重放、事件日志导出和一键运行生命周期压力测试。参数面板只在开发模式存在。

### 9.7 渲染技术决策

M3 实施时冻结为 Electron sandbox renderer + DOM/CSS 像素舞台，不引入 Canvas/PixiJS。原计划中的 Canvas/PixiJS 双实现 spike 被生产舞台证据替代，这是一次有记录的计划调整，不把未执行的 spike 伪装成完成。

选择依据：两款 V1 任务均是少量离散对象、HUD 和短反馈动画，DOM/CSS 已能提供语义化点击区、确定性状态检查和低成本视觉回归；当前构建约 24.55 kB JavaScript、10.96 kB CSS，真实 Electron 舞台 640×360，便携包内暖启动低于 500 ms，并通过 100 次生命周期和 30 分钟 soak。此时为比较而引入 PixiJS 会增加依赖、包体和沙箱验证面，但不会改善 V1 的用户结果。

当单场景同时活动 sprite 明显增加、需要 camera/filter/大量粒子，或 DOM 版本无法维持最低 30 FPS 有效节奏时，重新开启 Canvas/PixiJS 对照；替换只发生在 Stage renderer 内，不修改 Host、Runtime、Task Contract 或持久化合同。

### 9.8 数据记录

每个 session 本地记录：

- task、task version、asset version、difficulty policy version；
- seed、开始/结束时间、完成状态；
- 每试次刺激 ID、刺激属性、计划时间与实际呈现时间；
- 输入类型、输入时间、正确性；
- 命中、遗漏、虚报、抢答；
- 反应时统计和任务特定指标；
- 本局参数向量、升降级结果；
- 渲染掉帧、失焦、暂停等数据质量标记；
- 娱乐分数和触发的宠物反馈事件。

默认不联网，不记录屏幕内容、Agent 对话或用户正在处理的文件。

### 9.9 基础设施完成门

只有同时满足以下条件，才能开始 Go/No-Go 的正式内容开发：

- Stage Exerciser 可通过 Host Adapter 完整运行，不依赖任何任务规则；
- 连续自动打开/运行/关闭 100 次，无孤儿窗口、失效热点或未释放 session；
- 30 分钟持续运行无明显内存持续增长，目标 60 FPS，卡顿可被记录；
- 100%/125%/150% 缩放、主副屏、四个屏幕边缘均能正确锚定和收起；
- 鼠标和键盘事件带单调时间戳，暂停和失焦时间不会进入有效反应时；
- 固定 seed 的测试序列和事件结果可重复；
- renderer 异常不会拖垮宠物或 Agent 主窗口；
- feature flag 关闭后恢复原 OpenPets 行为；
- 接入一个第二测试模块不需要修改 Host、Runtime、Stage 或存储主流程；
- 自动测试覆盖状态机、窗口生命周期、任务结果校验和异常清理。

## 10. 难度与短局结构

V1 使用分块、可解释的确定性策略：

1. 第一关使用低负荷、强辨识刺激和即时反馈验证用户理解，不建立独立教学模式；
2. 正式局分成 2–3 个短 block；
3. block 之间只调整一个主要参数，避免无法解释变化来源；
4. 依据准确率、错误类型和有效反应时决定升级、保持或降级；
5. 具体阈值和参数优先级由认知任务负责人另行确认并版本化。

可以借鉴原始材料中的区间控制、脚手架和波浪进阶思想，但 V1 不把旧项目中的 75–90%、85% 等阈值直接当成通用规则。不同任务、短局长度和目标人群都可能需要不同策略。

## 11. 非功能要求

- 展开舞台到可交互：目标不超过 500ms；首次资源加载另行测量并优化；
- 舞台目标面积约为当前显示器工作区的九分之一，默认宽高约各占三分之一；
- 16:9 舞台建议限制在约 `480×270` 至 `720×405` 物理像素范围内，1920×1080 屏幕的典型尺寸为 `640×360`；
- 尺寸计算必须考虑 Windows 缩放和工作区，而不是随 4K 分辨率无限放大；
- 目标 60 FPS；连续掉帧必须写入数据质量标记；
- 输入时间戳使用单调时钟，不依赖动画帧序号；
- 宠物拖动、Agent 状态更新与任务输入不得互相误触；
- 支持 Windows 缩放、多显示器、任务栏在不同边缘的情况；
- `Esc` 永远可安全退出；崩溃不影响 Agent 和原宠物窗口；
- 完全离线可用；插件保持 sandbox，无 Node、任意导航或未批准网络访问；
- 至少提供音效总开关、降低动画选项和高可辨识刺激方案。

## 12. V1 验收标准

### 基础设施门

- 第 9.9 节所有条件必须先通过；
- 正式游戏只能依赖公开的 Runtime、Stage 与 Task Module 接口；
- 发现任务需要基础设施新能力时，先补充通用接口及测试，再继续任务实现；
- 不允许把游戏特殊逻辑临时写进 Host 或 Runtime 来赶进度。

### 产品闭环

- 用户能在不读产品说明书的情况下找到训练入口；
- 点击后能明确感到舞台由宠物发起，而非另一个 App 弹窗；
- 首次用户不经过教程页即可通过第一关理解规则；
- 两款任务均能在 60 秒左右完成、结算并回到桌面；
- 用户从点击宠物到开始作答无需选择游戏或关卡；
- 成绩会引发可感知但不打扰的宠物反馈；
- Agent 工作状态不被任务窗口破坏。

### 任务完整性

- 两款任务都有已评审的映射表和污染检查；
- 关键刺激时序、输入与指标有自动测试；
- 相同 seed 和参数能复现相同试次；
- 暂停、失焦和掉帧不会静默产生有效成绩；
- 新增第二款任务不需要修改 Host 窗口代码。

### 视觉质量

- 不出现诊断文字、默认 HTML 控件或临时占位美术；
- 像素在常见 Windows 缩放下保持清晰；
- 宠物、舞台、两款任务属于同一视觉世界；
- 开始、正确、错误、连贯、升级、结束都有定稿动作或效果；
- 实机录屏通过一次独立视觉评审，而不只验收静态稿。

### 稳定性

- 连续开关 20 次无残留窗口和失效热点；
- 拖动宠物后舞台锚点正确；
- 主副屏、屏幕边缘、缩放 100%/125%/150% 通过；
- 任务中 Agent 完成、宠物状态变化、锁屏恢复均有确定行为；
- 关闭 BrainPet feature flag 后恢复 OpenPets 原行为。

## 13. 开发计划

### M0：需求冻结与证据包（当前阶段）

交付：本 PRD、竞品转换案例、原始材料索引、V1 边界。  
退出条件：确认“先完成稳定基础设施，再制作两款游戏”，不扩成课程或平台。

### M1：基础设施合同与 Stage Exerciser 规格

工作：

- 冻结 Host Adapter、Runtime、Stage 和 Task Module 的职责边界；
- 定义状态机、时钟、输入、事件、资源和持久化合同；
- 定义 Stage Exerciser 的确定性测试场景；
- 建立基础设施自动测试与压力测试清单。

退出条件：接口、事件 schema、生命周期和基础设施完成门可直接指导实现。  
暂估：2–4 个聚焦工作日。

### M2：OpenPets Host Adapter

工作：

- 在 feature flag 下实现热点与锚定窗口；
- 实现窗口消息、宠物反应与插件沙箱最小接口；
- 验证拖动/点击冲突、透明点击穿透、焦点、多屏和缩放；
- 保证完全回退到原 OpenPets 行为。

退出条件：Host 能稳定承载一个不含游戏逻辑的锚定沙箱窗口。  
暂估：4–7 个聚焦工作日。

### M3：Runtime Core 与通用 Stage

工作：

- 依据生产舞台测量冻结渲染技术，并记录替代 Canvas 2D/PixiJS 对照 spike 的原因与重开条件；
- 实现状态机、时钟、输入、任务注册、session 和持久化；
- 实现资源、sprite、动画、音效、HUD、暂停、结算和关闭；
- 接入 Stage Exerciser 和开发模式参数/日志工具。

退出条件：无任何正式游戏时，可以稳定完成宠物发起—舞台运行—输入—结算—宠物反馈—收起。  
暂估：7–12 个聚焦工作日。

### M4：基础设施硬化与完成门

工作：

- 执行 100 次生命周期压力测试和 30 分钟持续运行；
- 完成多屏、DPI、边缘、失焦、锁屏和异常恢复验证；
- 用第二个无业务测试模块验证任务接入无需改基础设施；
- 修复并关闭第 9.9 节全部基础设施验收项。

退出条件：基础设施完成门全部通过；未通过不得开始正式游戏。  
暂估：4–7 个聚焦工作日。

### M5：玩法与角色视觉定型

工作：

- 完成两张 `Task-to-Game Mapping` 与污染检查；
- 确定宠物训练部位、角色造型、调色板和共享道具；
- 为既有 Stage API 制作正式像素资源，不反向扩张 Runtime。

退出条件：两款游戏机制、参数边界和视觉资源规格可直接进入制作。  
暂估：3–5 个聚焦工作日，可与 M4 后段并行准备但不进入正式编码。

### M6：Go/No-Go 成品

工作：

- 仅通过 Task Module 和 Stage API 实现“装箱，还是放过”；
- 完成第一关规则测试、正式 block、分数、关卡和难度；
- 接入正式 sprite、动画、音效和任务指标测试。

退出条件：不修改 Host/Runtime/Stage 特殊逻辑即可达到产品验收标准。  
暂估：4–7 个聚焦工作日。

### M7：持续更新成品

工作：

- 仅通过相同接口实现“行囊不重样”；
- 验证集合更新、移出判断、关卡、分数和指标；
- 验证第二款正式游戏接入后基础设施仍无任务特例。

退出条件：新增第二款游戏无需修改 Host、Runtime、Stage 或存储主流程。  
暂估：4–7 个聚焦工作日。

### M8：整合 QA 与私测包

工作：

- 多屏、缩放、锁屏、Agent 状态并发、异常恢复；
- 输入和时序数据审计；
- 视觉、声音与新手理解测试；
- 私有安装包与回退说明。

退出条件：形成可让外部小范围用户连续使用的私测版本。  
暂估：4–6 个聚焦工作日。

总量级暂估为 5–7 个聚焦周，其中前 2–3 周优先用于 Host、Runtime、Stage 和基础设施硬化。最大不确定性是 OpenPets 窗口边界、透明舞台在不同 Windows 环境中的稳定性和正式像素美术产能。时间估算在 M2、M3 完成后重估。

## 14. 风险与控制

| 风险 | 表现 | 控制方式 |
| --- | --- | --- |
| 游戏化污染范式 | 玩家靠颜色显著性、故事规律或额外操作取胜 | 映射表、污染检查、任务负责人评审、行为数据验证 |
| “任天堂化”变成 IP 模仿 | 角色、素材、音效或画面过度相似 | 只借鉴表达原则，建立原创宠物世界与资产来源记录 |
| 透明窗口体验不稳定 | 抢焦点、点穿、越屏、宠物拖不动 | feature flag、M2 专项 spike、多屏验收 |
| 美术范围膨胀 | 两个任务变成两个完整世界 | 不建世界观；共用角色、舞台、HUD、道具和特效库 |
| 短局数据波动大 | 升降级和最好成绩缺乏稳定性 | 分离训练反馈与长期解释；不做跨任务总分 |
| 基础设施脱离真实内容 | Runtime 很完整但不适合两款首发游戏 | 合同只覆盖两款已知需求；Stage Exerciser 验证稳定性，正式游戏验证适用性 |
| 基础设施看似完成 | 能弹窗但计时、异常恢复和跨任务复用不稳定 | 独立 Stage Exerciser、压力测试和第 9.9 节完成门 |
| Runtime 过度泛化 | 为不存在的未来游戏建设复杂引擎 | 只实现两款首发游戏已知需要的任务无关能力 |
| Agent 完成打断任务 | 用户在主任务和游戏之间冲突 | 当前试次优先、明确提示、随时安全退出、不强制抢屏 |

## 15. 正式游戏开发前的三个内容决策

基础设施可先按 M1–M4 推进。M5 结束、正式游戏编码开始前，只需要确认三件事：

1. 宠物哪个显眼部位作为训练入口；
2. 确定角色造型、调色板和共享工作台/行囊道具；
3. 认知任务负责人批准两张 `Task-to-Game Mapping` 及其参数边界。

除此之外，天梯、商业化、更多游戏、长期能力体系和开放生态都不应阻塞 V1。
